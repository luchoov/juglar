How Juglar draws

Explorable 01 turned sound into numbers. This page follows those numbers onto the screen: how one small program colors every pixel, why colors are mixed as light, how a waveform is made to hold still, how often frames are drawn, and what each one costs. It mirrors Juglar's render crate and the oscilloscope in dsp.

01One small program, every pixel

The GPU doesn't draw a waveform or a bar. It runs one tiny program, a shader, once for every pixel of the window, all at the same time, and each run answers a single question: what color am I? The pixel knows only its own position and the frame's numbers (four band levels, 32 spectrum bars, 256 waveform points). From those it works out whether it is on the waveform's line, inside a bar, inside a meter, or background.

Below, the same logic runs in your browser, on a synthetic song. Make the pixels bigger to see the grid the program fills, and point at any pixel to see the question it answered.

To run a shader on every pixel, Juglar asks the GPU to draw one triangle twice the size of the window. Its visible part is exactly the window, so every pixel is covered once. Two triangles forming a rectangle would also cover it, but the pixels along their shared diagonal would run twice.

Optional, for the curious: the triangle (crates/render/src/common.wgsl) 
@vertex
fn vs_main(@builtin(vertex_index) i: u32) -> @builtin(position) vec4f {
    // Corners (-1,-1), (3,-1), (-1,3): a triangle twice the size of the
    // screen, whose visible part is exactly the screen.
    let corner = vec2f(f32((i << 1u) & 2u), f32(i & 2u));
    return vec4f(corner * 2.0 - 1.0, 0.0, 1.0);
}

The screen spans −1 to 1 in both directions. Vertices 0, 1, 2 become (−1,−1), (3,−1) and (−1,3).

02Mixing light, not numbers

Screens store colors as numbers from 0 to 255, but those numbers are not amounts of light. They follow a curve called sRGB, which spends more numbers on dark shades, where eyes are sensitive. A pixel at 128, "half", emits only about 21% of white's light.

This matters wherever colors are mixed: the soft edge of a line, a pixel half covered by a bar. Mixing the numbers makes those edges darker than they should be, and lines look thin and ropey. Juglar converts its colors to linear light, mixes there, and converts back at the end.

03Holding the wave still

Juglar shows the newest 21 milliseconds of the waveform every frame. Cut at an arbitrary point, a repeating wave starts at a different spot of its cycle each frame and jumps sideways: unreadable. An oscilloscope solves this with a trigger: it always starts drawing where the wave crosses zero going up. A repeating sound then lands in the same place every frame and looks still.

Real music has hi-hats crossing zero at random, so the trigger watches a low-passed copy of the signal, where only the bass and kick remain. A low-pass filter delays what it lets through, so it runs forward and then backward over the samples, and the two delays cancel.

Optional, for the curious: the trigger (crates/dsp/src/scope.rs) 
// The newest upward zero crossing that still leaves a full view after
// it. Without one (silence, or a bass below 47 Hz), show the newest.
let last_start = recent.len() - SCOPE_SPAN;
let start = (1..=last_start)
    .rev()
    .find(|&i| self.filtered[i - 1] < 0.0 && self.filtered[i] >= 0.0)
    .unwrap_or(last_start);

filtered is the forward-then-backward low-passed copy; recent the newest 2048 samples.

04Frames on time

A display refreshes at a fixed rate, and a new frame can only appear at a refresh. If frames are ready at a rate unrelated to it, some stay on screen for one refresh and others for two. Motion then stutters, even at a high average frame rate.

So Juglar aims at 60 frames per second but snaps to the display: it draws on every refresh, or every second, third… refresh, whichever whole number lands closest to 60. Pick a display:

Two more details keep the rhythm. The timer for each frame counts from the previous frame's deadline, not from "now", so small delays don't add up into a slower rate. And Juglar doesn't rely on vsync to set the pace: on the development PC the driver ignored it, and a loop without its own timer drew 1,400 frames per second.

Optional, for the curious: the pacer (app/src/main.rs) 
fn new(refresh_hz: Option<f64>, target_fps: f64) -> Self {
    let fps = match refresh_hz {
        Some(hz) => hz / (hz / target_fps).round().max(1.0),
        None => target_fps,
    };
    Self { period: Duration::from_secs_f64(1.0 / fps), next: Instant::now() }
}

fn frame_done(&mut self, started: Instant, drawn: bool) {
    self.next = if drawn {
        let next = self.next + self.period;
        if next < started { started + self.period } else { next }
    } else {
        Instant::now() + HIDDEN_RETRY
    };
}

After a long stall (the window was dragged), the deadline starts over instead of rushing out the missed frames.

05What a frame costs

At 75 frames per second each frame has 13.3 ms. Here is where they go on the development PC (GTX 1060, Windows 11, DirectX 12), measured, not estimated:

MeasuredValueWhat it shows
Drawing, on the GPU0.04 msThe picture itself is nearly free
Submitting + presenting0.5 msTalking to the driver costs ten times more than drawing
Whole process, DirectX 125.8% of a coreUnder 1% of the 8-thread CPU
Whole process, Vulkan6.4% of a coreIts driver does part of the work on a thread of its own
Half the frame rate3.1% of a coreCost follows frames, not pictures

The lesson shaped later decisions: drawing more costs little, drawing often costs. So Juglar will lower its frame rate while a game runs and stop drawing in silence. And the first measurement, which timed only Juglar's own thread, picked the wrong graphics API: counting every thread reversed it (decision D19).
