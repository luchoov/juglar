juglar / explorables / 03

Feedback and color

Explorable 02 drew what Juglar hears. This page is about drawing something to look at: a picture that is, every frame, a slightly changed copy of the one before, and the steps that turn it into colors. It mirrors Juglar's render crate: feedback.wgsl, composite.wgsl and the scene Tide in scene/tide.rs and scene/tide.wgsl.

01A picture made of its own past

Point a camera at the screen showing its own picture, zoom in a little, tilt it a little, and an endless tunnel appears. Juglar does the same in software. Every frame it takes the previous picture, warps it (zooms, turns, swirls), fades it a little, and paints one simple shape on top: a ring whose edge is the waveform. Nobody draws the tunnel. It is the ring's own past, carried outward.

Below, the whole loop runs in your browser on the synthetic song from explorable 02, with Juglar's numbers. The picture is small (the loop's images are 160×90 here, about a twelfth of Juglar's in each direction), but every step is the same. Move the controls; they multiply what the music asks for.

Three numbers set the character of the picture. Zoom carries the past outward, turn and swirl bend it, persistence decides how long it is remembered: the time for paint to fall to about a third of its strength. Push the zoom to zero and the ring just smears in place; push persistence up and the tunnel fills with fog.

Every motion is set per second and converted to this frame's step, so the picture moves at the same speed at 60, 72 or 75 frames per second: the zoom per frame is erate × frame time, the fade per frame e−frame time / persistence.

Optional, for the curious: one frame of the loop (crates/render/src/feedback.wgsl) 
let p = (position.xy - 0.5 * size) / unit - frame.center;
// Where was this pixel's paint one frame ago? Undo this frame's step:
// turn back, and shrink toward the center.
let turn = frame.rotation + frame.swirl * (1.0 - smoothstep(0.0, 0.7, length(p)));
let q = rotate(p, -turn) / frame.zoom;
let uv = ((q + frame.center) * unit + 0.5 * size) / size;

var ink = textureSampleLevel(previous, smooth_sampler, uv, 0.0).rg;
let inside = all(uv >= vec2f(0.0)) && all(uv <= vec2f(1.0));
ink = select(vec2f(0.0), ink, inside);
ink *= frame.decay;
ink.y += ink.x * frame.palette_drift;

// New paint goes over the old.
let paint = sources(p, 1.0 / unit);
ink = ink * (1.0 - paint.x) + paint.yz;

This runs once for every pixel of the half-size image, on the GPU. The JavaScript on this page runs the same lines in a loop.

02Painting twice

Tick "Paint only once" above. The ring is then painted at full strength into the loop every frame, and nothing is drawn on top. Each frame's ring lands almost exactly on the last one's, which has moved by less than a pixel, so it doesn't leave a trail: it leaves a solid band, and in the drop the screen fills with fog. The first version of Tide did exactly that.

So Juglar paints each shape twice. Into the loop goes a faint copy, 5 to 11% of its paint, where many faint copies add up into trails with structure. And at the very end, at full resolution, a sharp copy goes on top, so the present stays crisp in front of its blurred history (decision D22).

Optional, for the curious: the two paintings (crates/render/src/scene/tide.wgsl) 
// Paint for the feedback image: (coverage, ink × coverage,
// ink × palette position × coverage).
fn sources(p: vec2f, pixel: f32) -> vec3f {
    let coverage = ring(p, pixel) * knob(3u);
    return vec3f(coverage, coverage, coverage * (knob(4u) + knob(6u)));
}

// Paint on top of the final picture, in the same form.
fn overlay(p: vec2f, pixel: f32) -> vec3f {
    let coverage = ring(p, pixel);
    let ink = coverage * knob(5u);
    return vec3f(coverage, ink, ink * knob(4u));
}

ring measures how much of the pixel the waveform's line covers, across the curve's slope so steep parts keep their thickness.

03The warp works backwards

The obvious way to zoom a picture is to take every old pixel and move it outward. On a grid, that fails: spread apart, the moved pixels leave holes between them, and where the picture is squeezed or turned, several land on the same spot.

So the loop asks the opposite question, once for every new pixel: where was my paint one frame ago? Every new pixel gets exactly one answer, so there are no holes and no collisions. The answer rarely falls on a pixel's center, so the four nearest old pixels are blended (bilinear filtering), which also lets the picture move by a fraction of a pixel per frame.

04Why the loop stores floats

A screen stores 256 levels per color channel, whole numbers from 0 to 255. If the loop's images did too, fading would break. A dim pixel at level 25, multiplied by 0.98, is 24.5, which rounds back to 25. It never gets darker, and a ghost of every trail would stay on screen forever.

Juglar's loop images hold 16-bit floating-point numbers instead. They keep fading smoothly down to nothing, and they can go above 1 where paint piles up. Tick "Store the loop in 8 bits" in section 01 and switch to "the ink only": the faint haze that stays everywhere is the stuck paint (decision D21).

05A palette in twelve numbers

The loop stores an amount of ink and a palette position for every pixel, not a color. Colors are chosen at the end, from a cosine palette: for each of red, green and blue,

color(t) = a + b · cos(2π (c · t + d))

Each channel is a wave as t goes from 0 to 1. a sets its middle, b how far it swings, c how many swings, d where it starts. Twelve numbers make a whole smooth palette, the GPU computes it in a few instructions, and changing one number shifts it coherently.

Tide's palette makes only half a swing per channel (c = 0.5), so each channel moves one way the whole time: from sand (#dcc69a) through silver to steel blue (#6f9bd1), never through green. The first try went from blue through teal to sand, the colors of these pages brightened. On screen its yellow-greens turned to mud when dim, and trails are dim almost everywhere. Compare the second strip of the two presets. (The first try's exact numbers weren't kept; this preset is rebuilt from its description.)

The last plot is a safety check. A flashing saturated red is the most dangerous kind of flash for photosensitive viewers; a color counts as saturated red when red carries 80% or more of its light. Juglar kept every animated color at 75% or less, and a test swept the whole palette; the rainbow fails it. Decision D48 dropped that rule along with the flash limiter, so the check here is history.

Optional, for the curious: Tide's palette and its test (crates/render/src/scene/tide.rs) 
const PALETTE: Palette = Palette {
    a: [0.649, 0.692, 0.712],
    b: [0.214, 0.084, 0.108],
    c: [0.5, 0.5, 0.5],
    d: [0.0, 0.0, 0.5],
};

#[test]
fn the_palette_never_turns_saturated_red() {
    // Research policy: animated colors keep red under 75% of the light.
    for i in 0..=1000 {
        let c = PALETTE.at(i as f32 / 1000.0);
        let linear = c.map(|c| if c <= 0.04045 { c / 12.92 } else { ((c + 0.055) / 1.055).powf(2.4) });
        let red_share = linear[0] / linear.iter().sum::<f32>();
        assert!(red_share <= 0.75, "{red_share} at {i}");
    }
}

The palette is computed in sRGB, the screen's encoding, and turned into linear light before measuring how much of it is red.

06How bright is ink?

Ink has no upper limit; a screen pixel does. Cut ink off at 1 and every dense patch becomes a flat blot with a hard edge. Tone mapping squeezes any amount into 0..1 with a soft shoulder, the way film responds to light:

light = 1 − e−color × ink × exposure

Tone mapping works per channel: the palette's strongest channel saturates first and the others catch up, so very dense ink drifts toward white, like an overexposed photograph. The ring's line, painted with the most ink, glows nearly white at its core and keeps its color at the edges. Before that, a gentle contrast curve (ink² / (ink + 0.2)) lowers faint ink more than dense ink, so haze fades into the background and the trails' structure stays.

07Hiding the steps: dithering

Fading trails make slow, dark gradients, and a screen has only 256 levels. Across a dark area the color may change by one level every 30 pixels, and the eye sees each step as a band. The fix is to add noise: before rounding, each pixel gets a random nudge of up to one level, different every frame. A pixel whose true value is 3.3 shows 3 most of the time and 4 some of the time; on average, 3.3. The steps dissolve into a grain too fine to notice.

Two details. The noise is the sum of two random numbers (triangular noise): with one, the grain is stronger at some brightness levels than at others, and a smooth gradient shows faint stripes of grain. Pick "one random number" and look closely at the enlargement. And the noise is added in the screen's encoding (sRGB), where its 256 levels are evenly spaced.

Optional, for the curious: tone mapping and dithering (crates/render/src/composite.wgsl) 
let ink = max(stored.x, 0.0) * max(stored.x, 0.0) / (max(stored.x, 0.0) + 0.2);
let position_on_palette = stored.y / max(stored.x, 1e-4);
let hue = srgb_to_linear(palette(clamp(position_on_palette + frame.palette_shift, 0.0, 1.0)));
let light = 1.0 - exp(-hue * ink * frame.exposure);
let edge = length(uv - 0.5) * 1.4;
let c = BACKGROUND * (1.0 - 0.5 * edge * edge) + light;

let pixel = vec2u(position.xy);
let n = (pixel.y * 8192u + pixel.x) * 2u + u32(frame.seed) * 33554432u;
var encoded = linear_to_srgb(c) + (random(n) + random(n + 1u) - 1.0) / 255.0;

random is a hash of the pixel's position and the frame number, so the noise is different for every pixel and every frame without storing any.
